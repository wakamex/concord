# Functional equivalence as a decompilation target

A decompilation is usually judged by rebuilding the original binary byte for byte. This note proposes that a future decompilation project make functional equivalence its target instead: each reconstructed function must behave like the original, and no effort goes into making its bytes identical. The check it describes is differential testing: run the original and the reconstruction of each function from the same starting state and compare what callers can observe. Generating the inputs is the fuzzing part. Execution engines for this exist; the comparison and the model of a 32-bit Microsoft Visual C++ (MSVC) program's world do not, and they are most of the note.

It draws on concord's work on [gruntz-decomp](https://github.com/sushi-shi/gruntz-decomp); on two checkers already running on decompilation targets, [harvest-oracle](https://github.com/wakamex/harvest-oracle) and the native oracle of [crimson](https://github.com/banteg/crimson); on a verification harness built for a [rev.ng](https://rev.ng/)-based lifting project that checked rewrites of 1,525 Warcraft III functions; on published prior work, listed under "Prior work"; and on two reviews of earlier versions (docs/reviews/functional-equivalence-carbon-2026-11-17.md and docs/reviews/functional-equivalence-engine-carbon-2026-11-17.md).

## Why not byte matching

gruntz-decomp rebuilds the 1999 game Gruntz with MSVC 5.0 and has 4,080 of 4,426 functions byte-exact (92.18%). Its last few percent show what byte matching costs. Of the 110 open functions at 97% or more whose first difference is a register choice, giving them retail's registers alone (`concord regtrace`, which forces the code generator's own register grants) makes 21 byte-exact: the code generator's input from their current source already yields retail's bytes when only the order in which it handed out eax, ecx and edx changes. Searching with concord's source rewrites, hand reconstruction, model agents and a debugger reading of the code generator's allocator closed one of those 21. For the other 325 open functions, whether they are behaviourally right is unknown, and a byte-matching percentage cannot say which are right and which are wrong.

Byte matching is also only possible with the original toolchain. A project that recompiles with a modern compiler never produces identical bytes, so byte identity cannot be its measure of correctness at all.

## Byte identity as a shortcut proof

When a function rebuilt with the original compiler happens to come out byte-identical, it is proven equivalent for every input and path, provided everything its bytes refer to is also the original's: each relocation resolves to the original's symbol, and the data at those symbols (floating-point constants, jump tables, string literals, initializers) is the original's bytes, either compared or taken by linking against the retail image's data. Such a function needs no behavioural run. That is a certificate the check can accept, not a goal to pursue: the project spends nothing on reaching it, and it never applies to a recompilation with another compiler.

The other things byte matching is credited with do not need it either. Linking reconstructed code into the original executable needs compatible struct layouts, calling conventions and name mangling, which the detour rig in the build order below needs and checks anyway. Exception tables and destructor order on exception paths are checked by the behavioural gate's exception-path runs.

## The check

The behavioural gate runs the original machine code and the recompiled machine code of one function from the same starting state and compares what each does that its callers can observe.

### Starting state

- Start from real states, not random ones. Run the original program (the retail executable exists and runs) under instrumentation, with function-entry hooks or full-system tracing, through recorded play, and capture at each function's entry its registers, x87 and segment state, the memory it reads (copy-on-write page snapshots), and what each of its callees returned and wrote. Every object, vtable, list and DirectDraw descriptor in such a snapshot is valid without hand-written seeding. harvest-oracle, which starts from generated memory instead, reports that many of its cases fault a few pointer hops in, so code deep in a function is exercised less often; snapshots address that.
- Reach code those runs did not with mutations on top of real snapshots: scalar fields, counts within bounds, error results from callees (DirectX's DD_OK is zero, so an injected failure takes the error path).
- Where no snapshot reaches a function, allocate its inputs type-guided from the reconstructed headers: pointers into a controlled arena, objects stamped with their real vtable pointer, lists ended by NULL with a probability that grows with depth, enums within their values, page zero unmapped. Pointer inputs are allocated lazily, when the code first dereferences them, as Micro Execution and UC-KLEE do. Unconstrained inputs produce false failures when the original relies on a caller precondition (non-aliasing pointers, aligned buffers, bounded counts), as UC-KLEE's authors found, so a difference seen only on synthesized inputs is reported as such, not as a fail. Address-derived bytes (every unmapped byte a hash of its address) remain the last resort and do not terminate on linked structures.
- Respect the entry ABI: the direction flag clear, all x87 stack slots empty, a thread environment block mapped at fs so that structured exception registration works, and the x87 control word the running program actually has at that point. The C runtime's default is 0x027F, which sets 53-bit precision, but a library can change it: crimson found that Direct3D 8 leaves 0x007F (24-bit precision) during gameplay. Snapshots record it; synthesized states use the value measured in the running game.

### The world outside the function

- Map the original image's read-only data, vtables and initial data, and resolve the recompiled function's references to globals, string literals, constants, vtables and jump tables to the original's addresses (link it against the original image, or detour it into a copy of the retail executable). Without this, every reference differs by raw address.
- Stub callees, with each stub's behaviour taken from the callee's recorded effects in the snapshot or from its contract: the prototype (argument count, stack cleanup, whether a struct return goes through a hidden pointer, whether the result is in eax, edx:eax or the x87 stack), out-parameters written identically on both sides, allocators returning fresh arena memory, and volatile registers and flags clobbered after every stubbed call so code that wrongly relies on them surviving fails. A stub's result is keyed on its arguments and on the memory it reads as recorded, so a getter called again after the function changed its object returns the new value, not a stale one.
- Compare pointer arguments by what they point at. A pointer to a local passed to a callee (`GetClientRect(hWnd, &rc)`, or `Lock(..., &ddsd, ...)` with a `DDSURFACEDESC` the function filled in first) differs between correct builds, and the local lives in the function's own frame, which is otherwise excluded from comparison. At each call, every pointer argument is dereferenced by its parameter type and the pointed-to bytes are compared, padding masked, wherever they live; the stub's outputs are then written through each side's own address.

### What is compared

- At each call and at return, the state the rest of the program can see: memory outside the function's own frame (compared as state at those points, not as an ordered trace of stores, since a correct build may reorder, merge or drop independent stores; padding bytes masked), the call's callee and its arguments as described above, and at return the result as the prototype defines it (al for a bool, eax, edx:eax, st(0), or the hidden struct pointer echoed in eax), the stack pointer (which checks the bytes popped), the callee-saved registers ebx, esi, edi and ebp, the direction flag, and the x87 stack depth and control word.
- The function's own frame is excluded, and so are the incoming argument slots, which MSVC uses as scratch; this needs the function's argument size.
- MSVC 5.0's C++ exception handling (/GX) registers a frame through fs:[0] in any function with a local that has a destructor, writing the function's own stack pointer outside its frame. At calls the comparison treats that registration as part of the frame; at return fs:[0] must equal its value at entry, since a registration left behind corrupts the next unwind. Exception paths get their own runs in which a stub raises, which needs the unwinder itself: either the original's ntdll and C runtime mapped into the starting state, or an unwinder for MSVC's exception records written into the harness.
- Constructors return this in eax; member functions returning a struct by value always do so through a hidden pointer; variadic member functions and COM interfaces do not use thiscall.
- The prototype database that says which of these apply comes from the original binary: how its callers use the result, the callee's `ret N`, the registers the original reads at entry. Taking it from the reconstruction's headers would be circular, since a wrong prototype is one of the defects being checked for: a function wrongly declared `bool` would be compared on al alone and hide a wrong eax. Where the reconstruction's declaration disagrees with the original's evidence, that is reported as a difference.

### Results

- Pass (or certified, for a byte-identical rebuild with the original compiler, or proved, under "Formal proofs" below), fail, inconclusive (a run hit its instruction, page or other limit) and under-exercised. A behavioural pass needs a coverage floor on both the original's and the reconstruction's branches, since a branch only the reconstruction has (a wrong guard) is otherwise never counted; below the floor the result is under-exercised, not pass. Limits count instructions, not wall-clock time, so that an inconclusive result does not depend on host load; harvest-oracle does this with a hardware instruction counter.
- Branch coverage is not equivalence: covering both sides of `if (x > 100)` does not catch `x >= 100` or a signedness error. Inputs at boundaries (each comparison's constant and its neighbours, signs, zero, overflow) are part of the generated set, as in harvest-oracle's comparison-guided inputs, which pool the comparison constants of both versions.
- Floating point: MSVC 5.0 computes with the x87 unit, and exact comparison holds only when both sides round the same values at the same points. A recompilation that keeps an intermediate in a register where the original stored it to a 32-bit `float` slot (or the reverse) rounds differently, and that happens between two optimization levels of the same compiler, not only between x87 and SSE code. A tolerance does not fix it, since a last-bit difference can flip a comparison or a float-to-int truncation. A difference confined to floating-point values gets its own result class for review, kept apart from pass and fail, until a function's spill points are shown to match.

## Making a pass mean something

- Validate the harness on pairs known to be equivalent that are not byte-identical: the same reconstructed source compiled with different optimization, inlining and declaration order. Byte-exact pairs share stack layout, registers and addresses and hide every false failure a real recompilation causes. Floating-point functions in that suite are expected in the floating-point class above, not as passes.
- Seeded wrong variants (a flipped condition, a constant off by one, a missing or extra write, swapped arguments, a clobbered callee-saved register, an x87 stack leak) must fail; the suite reruns whenever the harness changes. harvest-oracle's mutation benchmark is a working instance: it compiles real Harvest functions with the original toolchain, applies changes that alter behaviour (swapped dependent reads, a changed constant, a dropped store, a changed comparison, an off-by-one loop bound, a NaN-only comparison) and changes that preserve it (independent statement reordering, local renaming, outlining), and reports detection and false-difference rates separately.
- Every input a tool skips is a counted class: an instruction the emulator or solver cannot execute, an offset format a parser ignores, an implicit register write a disassembler does not report. In the lifting project, one field check silently ignored every hexadecimal offset and reported zero problems.
- Every disagreement is attributed to one side before anything changes. Most of the lifting project's refutations were checker bugs, not defects: [Triton](https://triton-library.github.io/)'s instruction semantics, [Capstone](https://www.capstone-engine.org/)'s flag details and LLVM's register descriptions were each wrong somewhere. A behavioural check's failures point at real defects only once its own failures have been worked through.
- Two implementations agreeing proves nothing when they share a blind spot; compare their results item by item.

## Prior work

No published tool gives an equivalence verdict for 32-bit MSVC code. The execution machinery and several of the ideas above exist; the comparison and the MSVC world model are this note's own. Each source below was read for the claims made here on 2026-11-17.

Checkers already running on decompilation targets:

- harvest-oracle checks two builds of a function from the [Harvest](https://github.com/banteg/harvest) decompilation (Linux x86-64, GCC 4.4.3), one of which can be the original executable's own code. It runs natively in a C harness: the original's code is mapped non-executable so that calls into it trap, memory is mapped on first touch with bytes derived from the seed and address, and run limits come from a hardware instruction counter. It compares the outcome, the return value by declared type, the ordered calls with their arguments, and, for cases that return, every 8-byte word written to generated memory or to the executable's globals. It follows callees GCC could have inlined, so inlining differences are not reported, reruns differing cases with data shifted by 4 KB to flag layout dependence, and has the mutation benchmark described above.
- crimson's native oracle runs functions of Crimsonland's original executable (Visual C++ 6, 32-bit, x87) under [Unicorn](https://www.unicorn-engine.org/) and compares them bit for bit with their Python ports, in continuous integration. It maps the executable at its base address, fakes the thread information block at fs so exception prologues work, passes this in ecx, reads the full 80-bit st(0), stubs callees and imports, and reports any access to unmapped memory with the address, instruction and nearest symbol. It compares against a reimplementation, not a recompiled function, and its whole-run gate, which compares runs of the recovered C++ core against the Python port, is the whole-program replay described below.
- The lifting project's runner executes a function in two binaries under Unicorn from the same random registers, with address-derived memory and stubbed calls, and compares rax, the memory writes and the calls. It compares a binary with a jump-rewritten copy of itself, so both sides share a compiler and layout, and it handles only x86-64.

Published work:

- [D-Helix](https://www.usenix.org/system/files/usenixsecurity24-zou.pdf) (Zou and others, USENIX Security 2024) is the closest: it recompiles each decompiled function and compares symbolic models of the original and the recompilation with angr, approximating external calls and bounding loops. Over 93,000 functions decompiled by Ghidra and angr it flagged 4,515 incorrect decompilations. It targets Linux x86-64.
- [DecompileBench](https://arxiv.org/abs/2505.11340) (2025) swaps decompiled and recompiled functions into OSS-Fuzz programs, replays fuzzing corpora and compares side effects, over 23,400 x86-64 functions. [BinRec](https://download.vusec.net/papers/binrec_eurosys20.pdf) (EuroSys 2020) lifts 32-bit Linux binaries to LLVM and recompiles them, validated by running them. Liu and Wang (ISSTA 2020) test C decompilers by mutating programs and comparing recompiled outputs.
- [Micro Execution](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/microx.pdf) (Godefroid, ICSE 2014) runs any function of an x86 Windows executable, allocating the memory it dereferences on demand: the lazy input discovery above, without a second side. [Blanket Execution](https://www.usenix.org/system/files/conference/usenixsecurity14/sec14-paper-egele.pdf) (Egele and others, USENIX Security 2014) compares unordered sets of a function's effects, but as a similarity score, not an equivalence verdict. [IMF-SIM](https://cse.hkust.edu.hk/~shuaiw/papers/IMF.pdf) (Wang and Wu, ASE 2017) fuzzes functions from an identical reset state and scores ordered traces for similarity.
- [UC-KLEE](https://www.usenix.org/system/files/conference/usenixsecurity15/sec15-paper-ramos.pdf) (Ramos and Engler, CAV 2011 and USENIX Security 2015) checks two versions of a C function for equivalence from under-constrained, lazily initialized inputs, at the LLVM bitcode level, so it cannot take the original machine code.
- [WinAFL](https://github.com/googleprojectzero/winafl)'s persistent mode calls one function repeatedly inside a live 32-bit or 64-bit Windows process: prior art for the native rig. [wtf](https://github.com/0vercl0k/wtf) runs Windows code from snapshots (a full kernel crash dump taken from a virtual machine with a kernel debugger attached) on [bochscpu](https://github.com/yrp604/bochscpu), the Bochs CPU as a library, or on a hardware virtual CPU, with dirty-page reset between runs.
- Formal equivalence of x86 code ([DDEC](https://theory.stanford.edu/~aiken/publications/papers/oopsla13b.pdf), [semantic program alignment](https://theory.stanford.edu/~aiken/publications/papers/pldi19.pdf)) proves single loops without calls equivalent on x86-64. Refinement proofs from binary to C ([Sewell, Myreen and Klein](https://www.cl.cam.ac.uk/~mom22/pldi13.pdf) for seL4, FoxDec) and validation of lifters to LLVM ([Dasgupta and others](https://sushant94.github.io/publications/20pldi.pdf), [Alive2](https://www-old.cs.utah.edu/~regehr/alive2-pldi21.pdf)) need formal instruction and C semantics. None of these takes 32-bit PE code; the lifter validation applies to a rev.ng lift's LLVM stage, not to MSVC originals.
- Decompilation projects' own tools, [decomp.me](https://decomp.me/), [objdiff](https://github.com/encounter/objdiff) and [reccmp](https://github.com/isledecomp/reccmp), judge functions by assembly match; reccmp does so for old 32-bit MSVC binaries. None runs code.

## The engine

The engine runs both sides' machine code; it does not decide what to compare, where inputs come from or what callees do, which the harness supplies on any engine. Solver-generated inputs are inputs like any other, so the solver is a separate tool (see "Symbolic tools") and not a criterion for the engine. The criteria:

- CPU fidelity: x87 at the precision the control word sets, transcendentals, flags and segment bases, as the real CPU computes them.
- Operating-system runtime: exception dispatch is ntdll and the C runtime, not the CPU. No emulator supplies it for 32-bit Windows, so the harness maps those libraries into the starting state or implements MSVC's unwinder, whichever engine it uses.
- Reset and observation: restoring a snapshot between runs and finding which memory a run changed at each call. With callees stubbed, a function body runs thousands of instructions, so the cost per run is dominated by resets, memory diffs and calls into the harness, not instruction speed.
- Deterministic limits: an instruction count, not a timer, for runaway loops.
- Instrumentation: branch coverage and comparison operands for the coverage floor and boundary inputs.

What is known about each engine:

- Native execution. harvest-oracle shows it working for x86-64 Linux code: exact by construction, deterministic limits through the instruction counter, memory caught on first touch through the fault handler. For 32-bit PE code it is untried. Under [Wine](https://www.winehq.org/) the original's fixed addresses and snapshot heaps may collide with Wine's own memory, a virtual call into code that must be stubbed becomes a trap and a signal round trip, and comparing memory at every call needs write tracking on the pages involved.
- Unicorn. crimson's oracle shows it working for 32-bit MSVC x87 code, including thiscall and fs. Unicorn 2 is based on QEMU 5.0.1 and computes ten x87 helpers, among them fsin, fcos, fptan and fpatan, through the host's 64-bit double maths; basic arithmetic honours the control word's precision exactly. Current QEMU computes f2xm1, fyl2x, fyl2xp1, fpatan and fprem in 80-bit software but still uses host doubles for fsin, fcos, fsincos and fptan, so a newer base would not fix those.
- bochscpu. Computes x87 transcendentals in software, tracks and restores dirty pages, and is deterministic. wtf's measurements put it about 100 times slower than its hardware-virtualization backend on long runs, which matters less for short stubbed runs than reset cost does. It has no loader; snapshots come from a debugger dump or from the harness.
- angr. Its VEX translation keeps x87 values in 64-bit registers and ignores precision-control changes, and concrete runs go through Python. That rules it out as the engine; it remains a candidate input finder.
- [Qiling](https://qiling.io/). Supports stdcall, cdecl and the 64-bit Windows convention but not thiscall, and its own code states that exception handling does not work on 32-bit Windows. Its operating-system layer is unused when every callee is stubbed. Ruled out.

Two tests decide between native execution, Unicorn and bochscpu before the harness is built:

1. An x87 opcode suite run on each engine against the real CPU: the control words 0x027F, 0x037F and 0x007F, results near the limits of the 15-bit exponent range, the C runtime's `_ftol` with its truncating control word, `fcompp` with `fnstsw ax`, 80-bit loads and stores, and fsin, fcos, fptan, fpatan, f2xm1, fyl2x and fprem. Its failures define which functions an engine can judge, and so whether Unicorn's transcendental gap matters for Gruntz's code or can be handled by routing the functions that use those instructions to an exact engine.
2. A stress test on one real snapshot of the running game: 10,000 reset-and-run iterations of a function with about 20 stubbed virtual calls, reads of unmapped memory, an infinite loop and a stubbed exception, on native execution under Wine and on Unicorn, the two with working precedents, and on bochscpu if the first test shows Unicorn's x87 inadequate. Measured: time per reset, time per memory comparison at a call, and whether every run gives identical results.

## One harness, two producers

Reconstructed functions come from two kinds of producer: hand or tool-assisted decompilations such as gruntz-decomp, crimson and Harvest, for the functions byte matching does not close, and the lifting project's recompiled rev.ng output. They can share the engine, snapshot and reset layer, but not the front end or the comparison. rev.ng's output keeps an emulated CPU state: it calls rev.ng's and QEMU's helpers, which must run rather than be stubbed; computes floating point in software on that state rather than in the x87 registers; keeps an emulated stack pointer beside the native one; and refers to the original's addresses directly. It also has no headers, so its prototypes come only from rev.ng's analysis of the original. The comparison for it reads results out of that state, where the comparison for a hand decompilation reads registers and memory.

Harvest is on both sides: its decompilation has harvest-oracle, and it is also on the lifting project's list of binaries to lift, so one Harvest function could have a hand reconstruction and a lifted one checked against the same original. Gruntz's 346 open 32-bit functions come before Warcraft III's lifted functions, so the MSVC comparison is settled on a few hundred functions before it is generalized.

## Symbolic tools

A symbolic engine (Triton, or [angr](https://angr.io/)) is safest as an input finder: it solves for a state that reaches an untaken branch, and both functions then run from that state on the engine, so a wrong instruction semantics in the solver costs coverage, not correctness. Triton is a library of instruction semantics and taint fed from an external tracer, with no loader or executor; angr has both, and D-Helix uses it to compare symbolic models directly. Proving small loop-free functions equivalent outright trusts the engine's semantics, which the lifting project found wrong in several places, so such proofs need the semantics cross-checked against the engine on the same instructions first. The lifting project's per-step proofs (about 400,000 steps without a refutation, at 30 to 40 milliseconds per step) were facts about one program, not equivalence of two, and do not carry over as a scale estimate.

## Formal proofs

Proving a reconstructed function equivalent to the original for every input needs three formal models: the instruction semantics of x86, so the original machine code means something to a prover; the world, meaning what memory, globals and callees may do; and an invariant for each loop that cannot be unrolled. The first has to be cross-checked against real execution before it is trusted, as above. The second is the same problem the emulation harness has, stated in logic instead of sampled, and for a function that calls into MFC, DirectX or the game's own objects it means specifying every callee's behaviour formally, which is harder than recording it.

That makes proofs a tier for one slice of the functions, not the gate for all of them:

- Leaf functions without calls, and functions without loops, can be attempted with an SMT solver such as [Z3](https://github.com/Z3Prover/z3): arithmetic, bit manipulation, parsing, table lookups. Multiplication and division, floating point and table lookups over byte-addressed memory can make the solver time out, and unconstrained inputs give false counterexamples where the original relies on a caller precondition, so a proof attempt has a time limit and a counterexample is replayed on the engine before it counts as a failure. A proved function needs no behavioural run, like a byte-identical one.
- Functions with loops can be checked with the loops unrolled a fixed number of times: equivalence up to that depth, stronger than sampled runs and weaker than a proof. The result records the bound. DDEC and semantic program alignment prove single loops equivalent on x86-64 and show how far that can go.
- Everything else goes through the behavioural gate.

## A reimplementation with stated laws

A language built around machine-checked properties, such as [Bend 2](https://github.com/bendlang/bend), whose compiler demands a proof of each law a program declares in a `LAWS.bend` file whenever the program changes, fits a different project from this one. Its programs are pure and linear, without mutable memory or pointers, so stating a Gruntz function in it means first modelling memory and the world explicitly, and proving such a function equivalent to the original binary needs x86 semantics inside the language's logic, which does not exist. Laws state properties (a grunt's health never goes negative, a level can always be finished), not equivalence to a binary, so proving them does not show that a reconstruction does what the original did.

Where it fits is a clean reimplementation of a game's logic, a remake rather than a decompilation: the laws carry the specification, and the original binary, run through the behavioural gate or the replay rig, supplies concrete behaviour to test the laws and the reimplementation against. crimson's Python port, checked against the original's functions by its native oracle, is that arrangement without the laws.

## What per-function checks miss

Stubbed callees cannot see a function breaking a contract another relies on: an object left in a state its next method does not expect, a buffer sized differently, an order of side effects that only matters across calls. Whole-program replay covers this: recorded inputs replayed against the original and against the original with reconstructed functions linked or detoured in, comparing frames, saved games and network messages. crimson's whole-run gate does this for its recovered core.

## Build order

1. The two engine tests above, on the opcode suite and one Gruntz snapshot.
2. A rig that detours one reconstructed function into a copy of the retail executable, and deterministic replay of recorded play with it in place. It gives ground truth from the start and records the entry snapshots and callee effects the per-function runner needs.
3. A prototype and vtable database built from the original binary's evidence (conventions, argument sizes, struct returns, result registers), checked against the reconstructed headers, and address canonicalization between the original image and recompiled code.
4. The two-sided per-function runner on the chosen engine, with the comparison above, validated on equivalent-but-different builds and on a mutation benchmark like harvest-oracle's before it reports on anything.
5. Snapshot replay with mutation, then type-guided allocation for functions no snapshot reaches, then boundary and solver-generated inputs for untaken branches.
6. Proofs with an SMT solver for leaf and loop-free functions, and bounded checks for functions with loops, once the instruction semantics are cross-checked against the engine.

## Where it is hard for a game like Gruntz

The world is most of the work: Gruntz calls MFC (Microsoft Foundation Classes), DirectDraw and DirectSound, keeps much of its state in globals and long-lived objects, and walks MFC lists whose iterators advance through reference parameters. Snapshots from the running game should remove much of that work; functions that only run in rare states remain the hard cases. On an existing byte-matching project such as gruntz-decomp, the check would sort the 346 open functions into behaviourally passing, failing, under-exercised and not yet checkable, which is the measure of correctness a reader of its progress actually wants.
