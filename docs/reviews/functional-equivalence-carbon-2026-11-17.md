## 1. Headline: Would this check tell a project which functions are functionally correct?

**No.** Built as described in [functional-equivalence.md](file:///inputs/functional-equivalence.md#L11-L30), this harness is a bounded, low-coverage differential fuzzer, not an equivalence verifier. On a 32-bit MSVC C++/MFC/DirectX codebase, it will misclassify wrong functions as **pass**, reject correct reconstructions as **fail**, and dump most non-trivial functions into **inconclusive**.

### Where it says "pass" for a wrong function (false positives)
* **Uncovered branches and boundary values within covered branches:** The note reports random state reached 94 of 6,981 branches (1.35%) in its reference project ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L28)), yet Rule 4 only withholds `pass` for `inconclusive` and `not exercised` ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L27)). A function that aborts on line 2 (`if (hr != DD_OK) return;` or `if (!ptr) return;`) on every run is exercised, finishes within limits, agrees on the early return, and gets marked **pass** with 95% of its body dead. Even with concolic branch solving, **100% branch coverage is not equivalence**: once `x = 0` and `x = 200` cover both sides of `if (x > 100)`, a branch-guided solver stops and never catches `x >= 100`, wrong signedness (`sar` vs `shr` when solved inputs are positive), or integer overflow.
* **Read/call ordering and aliasing bugs hidden by no-op stubs:** Callees return a synthetic scalar without mutating memory ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L18)). If the original reads `this->hp` *after* calling `TakeDamage()` and a buggy reconstruction caches `this->hp` in `esi` *before* calling `TakeDamage()`, both read the exact same unchanged address-derived bytes in the harness and **pass**. In the real game, `TakeDamage()` mutates `this->hp`.
* **Floating-point tolerances masking control-flow and integer divergence:** A "stated tolerance" ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L29)) only patches final float comparisons; if an x87-vs-SSE rounding difference flips an internal comparison or shifts `_ftol` truncation (`3.9999999f -> 3` vs `4.0f -> 4`) on an input the fuzzer did not hit, game logic and replay determinism break silently.
* **Wrong assumption records:** Every pass is conditional on a per-function assumption record ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L29)). Mark a function `void` when retail returns a status in `eax`, or omit `edx` on a 64-bit return, and the harness ignores the broken output.
* **ABI violations omitted from "observable effects":** Clobbering `esi`/`edi`/`ebx`, leaking an x87 stack slot, or breaking SEH unwind tables all **pass** (see §3).

### Where it says "fail" for a correct function (false negatives)
* **Pointers to stack locals passed to callees (out-parameters):** Consider `RECT rc; GetClientRect(hWnd, &rc);`. Valid recompilations place `rc` at different stack offsets (`ebp-0x14` vs `ebp-0x20`), which the note admits ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L26)). That breaks the check three times in a row:
  1. Comparing call stack arguments ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L23)) sees two different pointers (`0x...fedc` vs `0x...fed0`) and **fails**.
  2. The stub computes its return value from "its arguments" ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L18)), hashes two different pointers, and returns **different results** to the two sides.
  3. The stub never writes `rc`, so subsequent reads of `rc.right` read uninitialized random stack bytes from two *different* offsets (`stack[ebp-0x14]` vs `stack[ebp-0x20]`) and diverge.
* **Unrelocated symbol and `.rdata` addresses:** Unless every global, string literal, vtable, jump table, `.rdata` float constant (`fld dword ptr [0x472008]`), and callee sits at the identical virtual address on both sides—which fails as soon as function sizes or constant pools shift—every call target, pushed string/vtable address, and global write differs by raw address. Worse, mapping every page outside the frame with address-derived bytes ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L17)) overwrites `.rdata` float constants and switch jump tables unless image sections are exempted and relocated.
* **Comparing memory writes "in order" ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L20-L22)):** Valid recompilations reorder independent struct field stores (`this->a = 1; this->b = 2;`), coalesce byte/word writes into `mov dword` or `rep stosd`, eliminate dead overwritten stores, and differ on uninitialized struct padding bytes during value copies. Comparing an ordered write trace instead of post-state memory (at call/return synchronization points, masked for padding) fails valid C++ constantly.
* **Dead scratch state at call sites and partial return registers:** At a `call` instruction, the CPU does not label which registers or stack words are arguments. Without exact prototypes for *every* direct and indirect/virtual callee, comparing "register and stack arguments" ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L23)) sweeps in dead `ecx`/`edx` or caller spill slots above the real arguments. Likewise, returning `bool` defines only `al`; comparing full `eax` fails whenever upper bits hold different scratch leftovers.
* **Compiler helper inlining mismatches:** One build inlines `memcpy` (`rep movsd`, emitting memory writes) while the other calls `_memcpy` (emitting a stubbed call and zero writes).
* **Randomized CPU state violating entry ABI ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L19)):** Randomizing `EFLAGS` sets `DF=1` half the time (making `rep movsd` walk backwards on one side vs `mov` stores on the other), and randomizing x87 `FTW` marks FPU stack slots non-empty so `fld` immediately overflows to `-1.#IND`.

## 2. Is the argument against byte matching sound, and what does byte matching give that this check does not?

**No.** The argument fails on the note's own numbers and conflates two completely different targets (closing the last few percent of a same-compiler decomp vs. replacing byte matching as the primary project gate, potentially with a modern compiler).

### The evidence refutes the headline claim
Look at the arithmetic in [functional-equivalence.md](file:///inputs/functional-equivalence.md#L7):
* `gruntz-decomp` already matched **4,080 of 4,426** functions byte-for-byte (**92.18%**), leaving **346** open functions.
* Of the 110 open functions at $\ge 97\%$ whose first diff is a register choice, forcing retail's register grants (`concord regtrace`) made **21** byte-exact.
* **21 functions is 0.47% of the binary and 6.1% of the 346 open functions.** Even inside the cherry-picked bucket of 110 near-matches starting with a register diff, **89 out of 110 (81%) did NOT become byte-exact** when given retail's registers—because in MSVC 5.0, an early register rotation is usually a symptom of a real source difference (temporary lifetime, implicit cast, expression evaluation order, wrong member type, missing inline), not pure allocator whim.

Concluding from 20 stubborn functions (6% of the tail) that *"A byte-matching project spends most of its late effort on functions that are already correct"* ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L7)) is false on its face. And for those 21 same-compiler register swaps, you do not need Unicorn, object seeders, or whole-program replays—`concord regtrace` or local SMT basic-block equivalence already decided them completely.

### What byte matching gives that this check does not
1. **Universal quantification over all inputs and paths:** Byte identity (plus checked relocations) proves 100% path, corner-case, NaN, and overflow equivalence with zero harness maintenance and zero solver blind spots. The note gives this half a sentence ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L9)).
2. **Drop-in ABI, CRT, and hybrid-linking compatibility:** Matching with the original compiler locks down struct layouts, `#pragma pack` padding, vtable order, name mangling, CRT heap sharing, SEH tables, and exact x87 instruction sequences. That lets a project link reconstructed `.obj`s directly into the retail executable incrementally and preserves save-game and lockstep-replay compatibility. Recompiling with a modern compiler ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L29)) destroys binary/ABI compatibility and deterministic FP behavior.
3. **Verification of cold/implicit compiler outputs:** Byte matching verifies SEH unwind tables (`__ehhandler$`), destructor ordering on exception paths, static initializers, and shared header inlines even on paths no test ever triggers.
4. **Instant, zero-assumption diagnostic signal:** `objdiff` runs in milliseconds, requires zero per-function assumption records or MFC object-graph scripts, never reports `inconclusive`, and points straight to the differing instruction instead of forcing engineers to debug Unicorn/Triton semantics.

**Does the note account for this?** Barely. It notes that byte identity certifies a function ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L9)) and that stubbed checks miss cross-call contracts ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L46)), pushing the burden onto late whole-program replay tests. It ignores hybrid linkability, global/type layout enforcement, exception unwind verification, and the engineering cost of trading a zero-config structural diff for 4,426 bespoke assumption records.

## 3. What the observable-effect comparison misses or gets wrong for 32-bit MSVC C++

Comparing return registers, writes outside the frame, calls with arguments, and `ESP` at return ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L20-L26)) gets 32-bit MSVC 5.0 C++ ABI wrong in every category listed:

* **`this` pointers:**
  * Standard MSVC `__thiscall` passes `this` in `ecx` and callee-pops stack args, **except** variadic member functions (`...`), which silently fall back to `__cdecl` (`this` pushed on stack, caller cleans up), and COM interfaces (`IDirectDraw`, `IDirectSound`), which use `__stdcall` (`this` at `[esp+4]`, callee cleans up).
  * **Constructors and deleting destructors must return `this` in `eax`** (and constructors with virtual bases / scalar-or-vector deleting destructors take hidden flag arguments on the stack). Treating constructors as `void` misses broken `eax` returns that crash chained `new` expressions.
  * **Multiple and virtual inheritance adjustors:** Base-class casts shift `ecx` (`add ecx, offset` if non-null) or index a virtual-base table (`vbtable`) in memory. With address-derived memory, `vbtable` offsets are huge 32-bit hashes that launch `ecx` into wild addresses; if one side uses an adjustor thunk and the other adjusts inline, call traces disagree.

* **Structure returns (`sret`):**
  * In 32-bit MSVC, free functions return $\le 4$-byte PODs in `eax` and 5–8-byte PODs in `edx:eax` (so `edx` is live return state for 8-byte POD/`__int64`, and dead scratch that *must* be ignored for 4-byte returns).
  * **However, two huge classes NEVER return in registers in 32-bit MSVC:** (1) *any* non-POD C++ type of *any* size (has a ctor, copy ctor, dtor, or vtable—e.g., 4-byte MFC `CString`), and (2) **every struct returned by value from a `__thiscall` member function, even a 4- or 8-byte POD like `POINT` / `CPoint`**. Instead, the caller allocates space in its own frame, pushes a hidden `sret` pointer (`[esp+4]`, with `ecx = this`), and the callee writes into `*sret`, **returns `sret` in `eax`**, and pops `sret` (`ret N+4` in `__thiscall`/`__stdcall`; caller-popped in `__cdecl`).
  * In this harness: when testing a struct-returning function, random `[esp+4]` makes `sret` a random pointer that can alias globals or the callee's own frame; when *calling* a stubbed struct-returning function, the caller passes `&local_temp` (different stack addresses on each side -> false fail), and the stub returns a call-count hash in `eax` instead of echoing `sret`, crashing the MSVC caller when it dereferences `[eax]`.

* **Exceptions (32-bit Windows SEH and `/GX` C++ EH):**
  * Under MSVC 5.0 `/GX` (standard for MFC), **every function containing a local object with a destructor (e.g., `CString`)—even with zero `try`/`throw` keywords**—executes `mov eax, fs:[0]; push eax; mov fs:[0], esp` in its prologue, updates `[ebp-4]` (`trylevel`) across scopes, and restores `fs:[0]` in its epilogue.
  * First, Unicorn leaves `FS` base at `0` unless a Windows TEB is mapped. Second, `fs:[0]` is **outside the function's stack frame**, and `mov fs:[0], esp` **writes the function's own `ESP` to it**. Any frame-size or push-order difference writes a different stack pointer to `fs:[0]`, immediately failing the ordered "memory writes outside the frame" check!
  * Third, because `[ebp-4]` (`trylevel`) is inside the frame (excluded) and stubs "return at once" without raising SEH exceptions via `fs:[0]`, `catch` blocks and `__ehhandler$` unwind funclets have **0% coverage**; wrong destructor unwind order passes every time.

* **x87 FPU state:**
  * `float`/`double` functions return in `ST(0)`, not `eax`/`edx`.
  * **x87 is an 8-slot circular stack (`TOP` in `FSW`, occupancy in `FTW`), not flat registers.** Win32 ABI requires all 8 slots empty at entry (`FTW = 0xFFFF`), 0 slots left on exit for non-FP returns, and **exact net +1 (`ST(0)` valid, `ST(1..7)` empty)** for FP returns. Ignoring `FTW`/`TOP` lets an x87 stack leak (`fst` instead of `fstp`) **pass**; in the live game, 8 calls overflow the x87 stack and turn every float into `NaN`. Likewise, stubs for FP-returning callees *must* push onto `ST(0)` or the caller immediately underflows.
  * `FCW` (control word) must be initialized to MSVC's `0x027F` (53-bit mantissa, round-to-nearest—not hardware reset `0x037F`, and definitely not randomized) and checked at exit if modified (e.g., `_ftol` rounding-mode toggles).

* **Callee-saved registers (and volatile clobbers):**
  * `ebx`, `esi`, `edi`, and `ebp` (plus `EFLAGS.DF == 0`) are **missing** from the observable effects list ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L20-L26)). A broken reconstruction or inline `__asm` block that corrupts `esi` (where MSVC 5.0 habitually caches `this` in callers) passes the check and crashes its caller.
  * Conversely, at stubbed `call` sites, the stub must actively clobber volatile registers (`eax`, `ecx`, `edx`, status flags, x87 stack); leaving `ecx`/`edx` intact lets buggy code that assumes volatiles survive across a call pass.

* **Writes through pointers into the caller's frame (and incoming stack-argument slots):**
  * At entry (`ESP = ESP_0`), where does "the function's own stack frame" end?
  * In 32-bit MSVC x86, the incoming stack argument slots `[ESP_0 + 4 .. ESP_0 + 4 + arg_bytes)` sit *above* `ESP_0`, **yet belong to the callee as mutable scratch space**—MSVC 5.0 routinely increments by-value parameters in place (`add dword ptr [ebp+8], 1`) or reuses dead `[ebp+8]` as a spill slot! If "outside the frame" means `>= ESP_0`, valid spill reuse of `[ebp+8]` triggers **false fails** everywhere.
  * Above `ESP_0 + 4 + arg_bytes` lies the caller's real frame, which the callee legitimately mutates via out-pointers (`foo(&caller_var)`) and `sret`. Random 32-bit pointer registers have near-zero chance of pointing into that caller stack region—and if a random or solver-chosen pointer accidentally lands `< ESP_0`, writes through `*out` corrupt the callee's own locals *and* get ignored by the harness because they fall inside the callee's frame. Separating callee-owned stack args from caller-owned locals requires knowing exact `arg_bytes` (which `ret 0` in `__cdecl` never tells you).

## 4. Where the deterministic world breaks down, and what to do instead

### Where it breaks down
* **Address-derived memory (`mem[p] = f(p)`):**
  * **Non-termination on linked structures and strings:** Lists, trees, and MFC chains end at `NULL` (`0`). When every page maps to deterministic non-zero pseudo-random bytes ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L17)), `for (p = head; p; p = p->next)` chases hashes across newly mapped pages forever until hitting the step/page cap (`inconclusive`). Even `wcslen` walks ~64K bytes before stumbling on `0x0000`. And mapping page `0` on demand suppresses null-dereference crashes.
  * **Garbage loop bounds, enums, and floats:** An object count field `[ecx+0x10]` becomes `0x64b8192a` (1.6 billion iterations -> `inconclusive`). A `switch (this->state)` with 6 valid states hits `default:` 99.9999999% of the time. Address-derived IEEE-754 floats frequently decode as `NaN`/`Inf` or `10^30` (overflowing to `+Inf == +Inf` and masking real math bugs).
  * **Broken virtual/COM dispatch:** In `mov eax, [ecx]; call [eax+0x14]`, `[ecx]` (`vptr`) is a hash and `[vptr+0x14]` is another hash. The harness has no idea which virtual method was called, what its arity is, or what `N` to pop from `ESP` for `__thiscall`/`__stdcall`—corrupting `ESP` immediately after the first virtual call.
  * **Zero intentional aliasing:** Random 32-bit pointers never exercise valid aliasing (`p == q`, `this == &rhs`).

* **Call-count-derived stub results (`ret = g(seq, args)`):**
  * **`HRESULT` / `DD_OK` early-exit paralysis:** DirectDraw and DirectSound return `DD_OK == 0` on success. A hash-derived 32-bit return value equals `0` with probability $2^{-32}$. Every function starting with `if (lpDDS->Lock(...) != DD_OK) return;` fails the check on Call #1 and exits before running any game logic.
  * **Fragility under benign call-count changes:** If valid C++ calls a pure getter (`GetWidth()`) twice instead of caching it in a temp, Call #2 gets a *different* value from Call #1 (`g(2, ...)` vs `g(1, ...)`), and shifts the sequence index `seq` by $+1$ for every remaining call in the function, causing total cascade failure.
  * **Dead allocators and mutating iterators:** `operator new` returning a random hash can collide with stack/globals instead of yielding fresh zero/uninitialized heap memory. Iterator helpers like MFC's `CPtrList::GetNext(POSITION& pos)` advance `pos` via reference; a no-op stub leaves `pos` unchanged, turning every MFC list loop into an infinite loop.

### What to do instead for object- and pointer-heavy code
1. **Harvest real memory/register snapshots from the running retail binary first:** You have `GRUNTZ.EXE` and it runs. Instrument function entries and exits during gameplay/replays (via binary hooks, QEMU TCG plugin, or time-travel debugging traces) to capture copy-on-write page snapshots, CPU/FPU/TEB registers, and real callee return/out-param effects. Every MFC object, vtable, `CPtrList`, DirectDraw surface descriptor, and `NULL`-terminated chain is automatically valid without writing a single manual seeder. Mutate scalar fields and inject error returns on top of those real snapshots to reach cold branches.
2. **Link against the real binary image (or a canonical symbol map):** Map the actual read-only `.rdata`, vtables, and initial `.data`, and resolve symbols between the original and recompiled code to shared canonical addresses (or binary-detour the recompiled function directly into the retail image).
3. **Type-guided lazy arena allocation (bounded micro-execution), not `hash(addr)`:** Keep `0x0000..0xFFFF` unmapped. Using the reconstructed C++ headers/PDB types, allocate pointer roots into a controlled heap arena where dereferencing a pointer field lazily binds `NULL` with probability increasing by depth (guaranteeing finite trees/lists) or allocates a fresh typed object stamped with its **real class vtable pointer**, small bounded counts (`0..8`), valid enum values, and controlled aliasing.
4. **Contract-aware stubs driven by C++ prototypes:** Key pure getters on `(callee, canonical_args)` rather than `call_index`; make `HRESULT`/`BOOL` stubs return `0`/`TRUE` with high weight (and error codes on targeted runs); make allocator stubs bump-allocate from a dedicated canonical heap; and have stubs populate pointer out-parameters (`sret`, `RECT*`, `POSITION&`) from canonicalized buffer IDs so differing stack offsets get identical data.

## 5. Is the build order right? What to build first, and what is missing?

**No.** Step 1 has a fatal validation flaw, Step 2 scales poorly by design, and Step 4 is backwards.

### Why the proposed build order fails
* **Validating Step 1 on byte-exact functions ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L54)) proves almost nothing:** Byte-exact pairs have the *exact same* stack layout, register choices, store order, `ESP` at `mov fs:[0], esp`, `[ebp+8]` spills, and raw addresses. Every single false-negative bug caused by genuine recompilation (shifted `&local` out-params, reordered stores, dead scratch differences, padding bytes, relocation offsets) is **completely invisible** on byte-exact pairs! Worse, if a bad world causes both copies to bail out at instruction 4 (`hr != DD_OK`), byte-exact validation counts that as a green test.
* **Putting per-function assumption records in Step 2 ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L55)):** Hand-curating calling conventions, stub lists, and object seeders for hundreds or thousands of functions is slow and error-prone; metadata must come automatically from PDB/AST types and binary analysis.
* **Delaying whole-program replay until "enough functions pass" ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L57)):** In a binary decomp where you already possess the working retail `.exe`, you can detour/link *one* reconstructed function into the retail binary on day one. Replay tests give immediate ground truth and generate the real state snapshots needed by the per-function runner.

### What is missing entirely
* **Symbol relocation & address canonicalization** across original and recompiled code (globals, `.rdata` floats, jump tables, vtables, string literals, stack-local pointer provenance).
* **Callee signature & vtable dispatch database** (needed at *every* call site to know `ret N` stack cleanup, argument count vs. scratch registers, `sret`, and `ST(0)` returns).
* **32-bit Windows/MSVC runtime ABI scaffolding** (mapped TEB/`fs:[0]`, `DF=0`, `FCW=0x027F`, `FTW=0xFFFF`, non-volatile `ebx`/`esi`/`edi`/`ebp` checks, volatile register clobbering at stubs, post-state memory comparison at synchronization points).
* **A non-byte-exact ground-truth validation suite** (same C++ source compiled across `/Od`, `/O1`, `/O2`, permuted local declarations, and inlining toggles—pairs that *differ* in machine code and stack layout yet are known equivalent).
* **Static/SMT equivalence fast-path** for small or near-matching same-compiler functions (closing the 21 register-permuted functions with 100% mathematical certainty before touching an emulator).

### What to build first instead
1. **Binary detour/linking rig + deterministic whole-game replay & snapshot harvester:** Patch single reconstructed functions into the retail binary, run deterministic replays, and dump real `(registers, CoW memory, callee I/O)` entry snapshots.
2. **Relocation- and ABI-aware two-sided runner, validated on *non-byte-exact* equivalent builds + mutants:** Implement post-state comparison between call/return barriers, stack pointer canonicalization, TEB/x87/callee-saved checks, and PDB-driven prototypes. Gate validation on recompilations with different flags/frame layouts *and* require a coverage floor before emitting `pass`.
3. **Snapshot replay + type-guided state mutation** per function (using Step 1's harvested states, then fuzzing scalars/error codes).
4. **Static SMT equivalence for small/loop-free functions + concolic branch solving rooted in valid snapshots** for cold paths.

## 6. Unclear, overclaimed, or self-contradictory points in the note

* **"Functionally correct" ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L59)) vs. low coverage ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L28)) and contract blindness ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L46)):** Steps 1–2 emit `pass` with random inputs alone (which reached 1.35% of branches in the note's own citation) and without inter-procedural checks, yet the conclusion labels this bucket *"functionally correct"*. A low-coverage pass is `under-exercised`, not functionally correct.
* **"Its failures point at real defects" ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L9)) vs. "Most of the lifting project's refutations were checker bugs" ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L35)):** The note pitches behavioral checking on clean defect signal, then admits most refutations in its own prior harness came from broken semantics in Triton, Capstone, and LLVM.
* **"Deterministic world... by construction" ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L16-L17)) vs. manual object seeding ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L29), [L50](file:///inputs/functional-equivalence.md#L50)):** Section "The check" presents address-derived pages as the world model, then Section "Where it is hard" admits this fails on linked structures and that *"most of the harness work, and most inconclusive results"* will come from seeding objects and globals—an entire subsystem left completely undesigned inside a hand-waved "assumption record".
* **Bait-and-switch with the Warcraft III `rev.ng` numbers ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L3), [L42](file:///inputs/functional-equivalence.md#L42)):** The note cites the 1,525-function Warcraft III project as foundational evidence, then reveals on [L42](file:///inputs/functional-equivalence.md#L42) that its successful scale metric (*"400,000 steps over six slices without a refutation, at 30 to 40 milliseconds per step"*) was a **single-program per-instruction invariant check**, immediately admitting two-function equivalence *"does not scale the same way"*. Meanwhile, the dynamic part of that project hit 94 of 6,981 branches ([L28](file:///inputs/functional-equivalence.md#L28)).
* **Proving straight-line functions "outright" with Triton ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L40)) right after proving Triton is unsound ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L35)):** Using Triton only to *find inputs* replayed in Unicorn is safe against Triton bugs; using the *same symbolic engine* to *"prove [functions] equivalent outright"* trusts instruction semantics the note five lines earlier caught zero-extending 32-bit shifts wrong.
* **Illogical `or` on x87 floating point ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L29)):** *"MSVC 5.0 computes with the x87 unit, whose precision and rounding a modern compiler does not reproduce, so floating-point results need a stated tolerance or exact x87 emulation on both sides."* If the modern compiler emits SSE2 instead of x87, **exact x87 emulation on both sides does nothing** to make SSE2 match 80-bit x87; and if you use an output tolerance, any internal branch or float-to-int cast (`_ftol`) that straddles a rounding boundary still diverges in control flow, memory addresses, or integer outputs.
* **One-sided coverage blind spot ([functional-equivalence.md](file:///inputs/functional-equivalence.md#L28), [L40](file:///inputs/functional-equivalence.md#L40)):** Coverage and symbolic solving only track branches of **the original** binary. Any spurious branch introduced only in the reconstructed function (e.g., a wrong guard, bounds bug, or macro expansion) is neither counted in coverage nor targeted by the solver.
* **Underspecified core mechanics:** How symbols/globals/vtables/constants are relocated between binaries, whether "compared in order" ([L20](file:///inputs/functional-equivalence.md#L20)) means raw store-by-store traces or barrier snapshots, where "the function's own stack frame" ([L22](file:///inputs/functional-equivalence.md#L22)) begins and ends relative to stack arguments, and how stubbed `stdcall`/`thiscall`/virtual calls adjust `ESP` are never defined.
